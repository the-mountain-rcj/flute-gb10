# GB10：A16 × FP4 E2M1，K 方向 group_size=128 的 CSV GEMM 测试

本说明配套 `benchmarks/bench_a16_fp4_g128.py`，在 Linux / ARM64 的 GB10（SM121）上尝试构建并调用原版 FLUTE。测试沿用 CSV 中的矩阵尺寸，权重使用 FP4 E2M1 数值及每 128 个 K 元素一个缩放因子；测试代码不添加或修改 CUDA kernel。

当前交付是源码与测试入口。FLUTE 上游的兼容性表没有列出 GB10，本文也没有提供 GB10 编译成功、正确性通过或吞吐量的实测结论。须依次完成下面的环境检查、构建、小规模正确性测试及正式测试。

## 1. 数据格式与计算口径

计算为 `C[M,N] = A[M,K] @ W[K,N]`。`--a-dtype bf16` 使用 BF16 激活，`--a-dtype fp16` 使用 FP16 激活；默认 BF16。输出、缩放因子及 LUT 使用与 A 相同的 16 位类型。

每个 4 位权重编码索引以下 E2M1 LUT：

```text
编码  0..7 :  0,  0.5,  1,  1.5,  2,  3,  4,  6
编码 8..15: -0, -0.5, -1, -1.5, -2, -3, -4, -6
```

对每个输出列 n，`W[k,n] = LUT[code[k,n]] * scale[n, k // 128]`。实际存储为每个权重 4 位和每个 K 分组一个 16 位 scale；没有把 g128 展开为多个 g16/g32 scale。4 位索引经过 FLUTE 原有 packing 重排，因此不能把它直接当作其他 FP4 库的 packed tensor 使用。

CSV 只提供尺寸，不提供模型权重。脚本生成合成权重，每组用 `absmax/6` 求 scale，先将 scale 舍入为实际存储的 16 位类型，再选择最近的 E2M1 数值；恰好位于相邻数值中点时向零取值。这个离线量化器用于 GEMM 测试，没有执行模型校准。

FLUTE 使用 LUT 在融合 GEMM 内解码权重，再执行 FP16/BF16 Tensor Core MMA。它实现 A16 与 E2M1 权重的计算语义，但不能把测试结果解读为硬件原生 A16×FP4 MMA 吞吐量，也不属于 NVFP4 g16 或 MXFP4 g32。计时调用原版 `flute.qgemm`，调优与打包调用原版 `flute.tune.tune_and_pack`。

### 2.1 安装前预检

```bash

```

该脚本仅使用 Python 标准库，检查 Linux ARM64、Python 3.12 的 venv/开发头文件、Git/C++ 编译器、CUDA Toolkit 13.0 的头文件及 SM121 编译目标、驱动可见 GPU 的计算能力，以及已有 venv / CUTLASS 目录是否冲突。它不导入或要求当前 PyTorch，直接查询 CUDA 驱动；安装脚本建立独立环境后才验证指定 PyTorch 版本及 CUDA 张量运行。磁盘和系统可用内存会给出余量提示，不把估算的建议值当成硬件支持条件。

## 4. 使用原版源码构建

上游 README 指定 CUTLASS `v3.4.1`，而 `setup.py` 将头文件路径写死为 `/workspace/cutlass/`。下面将该版本放入自己的 GB10 目录，并用编译环境变量提供头文件路径，无需修改 `setup.py` 或 CUDA 源文件。


构建命令：

```bash
cd "$HOME/GB10/flute-gb10"
export CUDA_HOME="$(dirname "$(dirname "$(readlink -f "$(command -v nvcc)")")")"
export CUTLASS_ROOT="$HOME/GB10/cutlass-v3.4.1"
export TORCH_CUDA_ARCH_LIST="12.1"

export CPATH="$CUTLASS_ROOT/include:$CUTLASS_ROOT/tools/util/include${CPATH:+:$CPATH}"
export CPLUS_INCLUDE_PATH="$CUTLASS_ROOT/include:$CUTLASS_ROOT/tools/util/include${CPLUS_INCLUDE_PATH:+:$CPLUS_INCLUDE_PATH}"

```

`NVCC_PREPEND_FLAGS` 为 nvcc 明确添加 include 参数，`CPLUS_INCLUDE_PATH` / `CPATH` 补齐主机编译器的搜索路径。如果机器原本存在 `/workspace/cutlass`，由于 `setup.py` 显式 include 目录也参与搜索，需确认它同为 `v3.4.1`；不同版本混用时应先调整构建环境。

`--no-build-isolation` 让扩展使用当前已确认的 PyTorch；`--no-deps` 避免自动安装上游整套模型依赖。`MAX_JOBS=1` 控制并行编译的内存占用。原版代码包含大量模板，编译可能耗时较长。

这些设置只指定编译目标，不能保证旧版 CUTLASS / FLUTE 与 CUDA 13、SM121 兼容。出现编译错误时，保留 `build-gb10.log` 中首个错误及版本信息；不要仅为让测试跑通而把目标改成其他 GPU 或修改内核后继续使用同一结果标签。

## 5. 检查 CSV，再运行小规模测试

输入列至少包含 `testcase_id,m,k,n`。注意 CSV 顺序为 **M、K、N**，不是 M、N、K。M 必须为正整数，K 必须为 512 的正整数倍，N 必须为 256 的正整数倍。K / N 的约束保守覆盖此次使用的原版 scale 向量读取及 packing / 模板布局；脚本不会静默 padding 或更改 CSV 尺寸。

```bash
  --csv benchmarks/data/a16_fp4_g128_smoke.csv \
```

`--dry-run` 只检查 CSV 与参数，不运行 GPU kernel，因此通过它不代表 GB10 已支持。

## 6. 运行大矩阵或已有 CSV

```bash
python benchmarks/bench_a16_fp4_g128.py \
  --csv benchmarks/data/a16_fp4_g128_large.csv \
  --result-csv results/a16_fp4_g128_large_bf16.csv \
  --a-dtype bf16 --target-sm 121 \
  --num-tests 30 --warmup 5 --tune-seeds 1 \
  --check-rows 32 --check-cols 512
```

使用已有尺寸文件时，将 `--csv` 改为该文件路径即可。第一次运行每种新尺寸 / dtype 时，原版 `tune_and_pack` 会尝试多个已编译模板，调优开销可能明显大于最终 GEMM 计时。增加 `--tune-seeds` 可以增加调优样本，但不代表以 E2M1 实际数据重新设计了 kernel。

大矩阵默认最多抽取 32 行、512 列进行正确性检查，索引均匀覆盖输出并包含首尾，**每个被检查输出都保留完整 K 归约**。参考权重由本次 E2M1 code 与 g128 scale 重建并舍入到 A 的 16 位类型，再将 A 和参考权重转成 FP32 做矩阵乘法；参考计算关闭 TF32。这衡量融合 kernel 的数值一致性，不衡量相对于原始全精度模型的量化损失。

结果会报告实际检查覆盖范围。`--check-rows 0 --check-cols 0` 可检查全部输出，但大矩阵的参考计算及内存开销随之上升。抽样通过不能等同于全输出通过。

正确性在首次普通调用和全部 CUDA Graph 重放结束后各检查一次。两次都扫描**全部输出**中的 NaN / Inf，并对指定输出位置检查数值；CSV 保留两次检查中较大的误差。

设抽取的输出为 `got`、对应参考为 `ref`，采用以下两项判据，必须同时小于各自阈值：

```text
diff        = max(0, 1 - 2*dot(got, ref) / (sum(got²) + sum(ref²)))
relative_l2 = sqrt(sum((got-ref)²) / sum(ref²))
```

| A 类型 | `--max-diff` 默认值 | `--max-relative-l2` 默认值 |
| --- | ---: | ---: |
| BF16 | 0.0001 | 0.011 |
| FP16 | 0.000003 | 0.002 |

`diff` 是相似度误差指标，不是逐元素最大绝对误差；相对 L2 阈值沿用上游对应 dtype 的容差。`max_abs` 另外记录被检查位置的最大绝对误差。全零参考使用脚本的零分母处理。通过这些判据不代表模型质量通过；失败结果应保留并检查，不能通过调高阈值后仍宣称原阈值通过。

可选的同精度稠密基线使用相同 A，以及在计时外反量化得到的 A16 权重，调用 `torch.mm`：

```bash
python benchmarks/bench_a16_fp4_g128.py \
  --csv benchmarks/data/a16_fp4_g128_smoke.csv \
  --result-csv results/a16_fp4_g128_smoke_bf16_baseline.csv \
  --a-dtype bf16 --target-sm 121 \
  --check-rows 0 --check-cols 0 --baseline
```

基线单独记录为 `baseline_us`，`speedup_vs_a16 = baseline_us / elapsed_us`。该值仅比较已打包的融合 W4A16 调用与已有稠密 A16 权重的 GEMM；不包含离线反量化时间，不得将基线结果标为 FP4 性能。基线需要额外分配完整的 16 位权重和输出。

## 7. 性能记录与边界

计时使用 CUDA Graph，每次重放执行一次原版融合 `flute.qgemm` 调用。`torch.cuda.Event(external=True)` 在图中产生显式事件节点，紧邻该调用前后，避免将 Python 提交间隙计入耗时。区间包括融合权重解码、MMA 和 Stream-K 归约，不包含主机端分配、随机数据生成、调优、packing、参考反量化或正确性比较。

默认每次重放都先向 256 MiB 缓冲区写零，再记录开始事件；刷新操作也被捕获在图中，但在计时区间之外。`--no-flush-l2` 关闭刷新。与采用约 8 GiB 刷新缓冲区的旧结果比较时，可显式加入 `--flush-mb 8192`，同时记录该选项。该写操作用于扰动缓存，不保证每条缓存线处于指定状态；不同刷新设置的结果应分别比较。

`elapsed_us` 为默认 30 次重放的中位数，另记录 `min_us` / `max_us`。`--num-tests` 控制正式测量次数，`--warmup` 控制预热，普通调用与图重放各有预热阶段；即使设为零，仍执行捕获所需的最小预热。吞吐量按稠密 GEMM 的 `2*M*N*K / time_seconds / 1e12` 计算，单位 TFLOPS，不使用稀疏倍数。

此前 DeepGEMM runner 使用 Kineto 的 kernel 平均时间，本脚本使用图内事件中位时间；即使刷新缓冲相同，也不是完全相同的统计方法。严格横向比较需要统一计时和缓存口径。这个 W4A16 实现执行 16 位 MMA，不能用 GB10 的 FP4 稀疏峰值计算它的算力利用率；低位权重主要减少权重流量，较大 M 时不保证比普通 A16 GEMM 快。

`gbps` 用以下逻辑字节数除以中位耗时，并换算为十进制 GB/s：

```text
2*M*K + N*K/2 + 2*N*(K/128) + 2*M*N
  A16     W4       scales       D16
```

这是 A、W4、scale、D 各计一次的有效数据量估算，**不是测得的 DRAM 带宽**，没有计入 LUT、临时缓冲、重复读取、归约流量等。GB10 为共享内存系统，大矩阵还会同时占用激活、输出、未打包索引、已打包权重、参考块和工作区的空间，不能只用 4 位权重文件大小估计峰值占用。

每个结果 CSV 会配套同名 `.metadata.json`，例如 `results/a16_fp4_g128_large_bf16.metadata.json`。它记录 GPU、计算能力、CUDA / PyTorch、库路径与 Git 提交、完整命令参数、量化及计时口径。CSV 中 `passed` / `error` 表示逐项验收状态，`checked_rows` / `checked_cols` 表示数值检查覆盖范围；`template_id` / `num_sms` 记录原版调优选择。请同时保存这两个文件和构建日志。

若没有可用模板、遇到 CUDA launch 错误、非有限结果或正确性未通过，该尺寸应记为失败，而不是零耗时或零误差。原版 Stream-K 归约可能存在非确定性，因此重复运行不要求逐位一致。

## 8. 大矩阵的条件性能估计（不是实测）

针对 `M=8192, K=1536, N=65536`，按稠密矩阵乘的口径：

```text
FLOPs = 2*M*N*K = 1,649,267,441,664
```

FLUTE 读取 4-bit 权重后，在融合内核中解码为 BF16/FP16，执行的是 **16 位 MMA**。这里用 GB10 dense A16 峰值约 **125 TFLOPS** 建模：该值是根据 [NVIDIA 公布的 GB10 FP4 稀疏峰值](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)及 [RTX PRO Blackwell 的不同精度比例](https://www.nvidia.com/en-us/data-center/rtx-pro-6000-blackwell-server-edition/)推算的，不是 NVIDIA 单独公布的 GB10 BF16 规格，也不是本机实测。

由此得到理想计算下限 `1.649267e12 / 125e12 = 13.194 ms`。不能使用 dense FP4 约 500 TFLOPS 或 sparse FP4 1000 TFLOPS 为该内核估时。

若 A、权重和 scale 各读一次、输出只写一次，理想最低逻辑流量为：

| 数据 | 大小 |
| --- | ---: |
| A16 | 24 MiB |
| FP4 权重 | 48 MiB |
| g128 的 16 位 scale | 1.5 MiB |
| 16 位输出 | 1024 MiB |
| 合计 | 1097.5 MiB，即 1.150812160 GB |

按官方 273 GB/s，理想带宽下限约 4.215 ms。理想下限模型取计算与带宽下限的**最大值**，不是相加，因此该模型给出约 **13.2 ms**。实际内核会重复读取数据、执行查表/反量化及 Stream-K 归约，不能把最低逻辑流量当成实际 DRAM 流量。

以下只是条件推算，不是测得的效率：

| 假设 A16 峰值有效利用率 | 有效吞吐 | 耗时 |
| --- | ---: | ---: |
| 30% | 37.5 TFLOPS | 44.0 ms |
| 40% | 50 TFLOPS | 33.0 ms |
| 50% | 62.5 TFLOPS | 26.4 ms |
| 60% | 75 TFLOPS | 22.0 ms |
| 70% | 87.5 TFLOPS | 18.8 ms |

可以暂按 **20–40 ms** 做低置信度规划（对应约 33%–66% 有效利用率），但这不是保证范围、置信区间或正确性通过标准，实际 FLUTE 表现可能更慢。此前同尺寸 MXFP8×MXFP4 的 11.584 ms，若仅假设换成 A16 后保持相同峰值利用率，则约为 23.168 ms；两个不同内核的利用率并没有理由必然相同，不能据此承诺恰好慢两倍。

这些时间指结果中的单次 GPU 调用时间，不包含安装、编译、首次调优、权重打包或正确性参考计算。最终应报告实测 `elapsed_us`、`tflops` 和配置，并用 `--baseline` 对照同机 A16 GEMM。
